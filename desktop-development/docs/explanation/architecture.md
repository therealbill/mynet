# Why Wails v3 and Go

The desktop-development plugin makes one large architectural bet and several smaller ones that follow from it: a desktop app is a single Go process that owns a webview, and the only contract between Go and the UI is a set of generated TypeScript bindings. This page explains where that bet came from, what the boundaries inside a project are, why macOS gets the detailed treatment, and what accepting a beta framework costs. The plugin previously targeted Electron with a separate Go backend process and dropped it entirely in the 2.0.0 release.

## The problem: the boundary is the cost

Pairing a web-technology UI with a Go backend is a reasonable instinct. Go is good at concurrency, file and database work, and system integration; the web stack is good at interfaces. The usual way to combine them is to run them as two operating-system processes and put a local network protocol between them — HTTP for request/response, WebSocket for push — and that arrangement sounds clean when drawn as a box diagram.

The plugin owner rebuilt a real application from that architecture and measured what it actually cost. The results are what this plugin is built around.

**Size.** The packaged two-process application was 283 MB: 221 MB of bundled browser runtime plus a 50 MB universal Go binary. A freshly scaffolded Wails v3 React application, measured on the same Mac, produced a 10 MB `.app`. The scaffold check for this plugin's skill built a 9.3 MB binary in about eight seconds including `npm install`.

**Code.** Roughly 80 percent of the old codebase existed to bridge process boundaries or was unreachable. The Go side was 37,685 non-test lines, about 70 percent of it generated by an API framework whose only job was to describe a contract between two halves of the same application. The TypeScript side was about 16,700 production lines, of which roughly 55 percent was boundary plumbing and 25 percent was dead. The application had five distinct process boundaries — renderer to preload script to main process to a spawned Go server to a second local HTTPS server for OAuth — and delivering a single OAuth result across them had accumulated about 3,200 lines of queueing, acknowledgements, readiness signalling, retries, runtime validation, and debug logging, plus six design documents recording successive attempts to make it reliable.

None of that code implemented a feature. It existed because there was a boundary.

## One process, generated bindings

Wails v3 removes the boundary rather than making it more comfortable. The Go program embeds the built frontend and creates a webview window inside its own process. Services are ordinary Go structs registered at startup; `wails3 generate bindings` reads their exported method signatures and writes TypeScript functions into `frontend/bindings/`. The frontend imports those functions and calls them.

```
Two processes                      One process
-------------                      -----------
UI  --HTTP/WS-->  Go server        UI  --generated binding-->  Go service
 |                    |             (same process, same types)
 hand-written client  hand-written
 duplicate types      handler + DTO
```

What disappears with the boundary:

- **The client.** There is no fetch wrapper, no base URL, no retry policy, no port allocation, no health check, no lifecycle supervision of a child process.
- **The duplicated type.** An entity is declared once as a Go struct under `internal/domain`. The binding generator emits its TypeScript shape. A field rename is a compile error on both sides after one command, not a runtime surprise.
- **The serialization contract.** A `context.Context` first parameter becomes a cancellable promise. A returned `error` becomes a rejected promise. Nobody designs an error envelope.
- **Polling.** Go pushes to the UI with typed events registered at `init()` and emitted with `app.Event.Emit`. Streams carry token-by-token output. There is no interval timer asking whether anything changed.

The trade-offs are real and worth naming:

| Gained | Given up |
| --- | --- |
| One deployable artifact, ~10 MB instead of ~283 MB | The frontend cannot be pointed at a remote API without writing one deliberately |
| Types defined once, checked by the compiler | Regenerating bindings becomes a required step after any service signature change |
| No process supervision, ports, or readiness protocol | Go and the UI share a failure domain; a panic takes the window with it |
| Native APIs reachable directly from Go | The webview is WKWebView on macOS, not Chromium, so Chromium-only APIs are unavailable |
| No bundled browser runtime to ship or patch | The rendering engine is the user's OS webview, and varies with their OS version |

The generated bindings are committed to the repository so a fresh checkout builds without running the generator first. That is a small decision with an outsized effect: it keeps the contract visible in code review rather than hidden in a build step.

## The adapter boundary

Removing the process boundary does not mean removing all boundaries. It moves the important one inside the binary, where it costs a package import rather than a network hop.

```
main.go              wires services, calls startDesktop
main_desktop.go      //go:build !server   window, menu, tray, shortcuts, notifications
main_server.go       //go:build server    startDesktop is a no-op
app/                 thin Wails adapters, one file per native concern
internal/domain/     entities and rules; imports neither Wails nor a store
internal/store/      persistence behind interfaces
cmd/<tool>/          optional CLI or TUI entry points that import internal/ only
```

Three rules hold this together.

**`app/` is thin.** Each native concern — window, menu, tray, notifications, shortcuts — gets one adapter file that translates between Wails types and plain functions and channels. No business logic lives there. Wails v3 is a beta that has shipped breaking changes inside its own beta series, and confining its types to one directory means an API change touches adapter files rather than the application.

**`internal/` never imports Wails.** Domain types and rules have no idea a window exists. This is what makes the layout worth the discipline: a Cobra CLI or a Bubble Tea TUI under `cmd/` imports exactly the same packages the desktop app does, with no shim and no duplicated logic. The desktop shell becomes one entry point among several rather than the program itself. That is also why the agent treats "give my Go tool a small status window" as an architectural moment — the shared-internals layout has to exist before the first window does, not after.

**Every native feature has a `server` build-tag stub.** `task build:server` compiles with `-tags server,production` and produces a binary that serves the same frontend and the same bindings over HTTP, with each browser tab acting as a window. Server mode has no tray, no native dialogs, no native windows, no shortcuts, and no notifications — hence the stubs. What it buys is a build that a browser automation suite can drive: `playwright-expert` can exercise the real services and the real bindings without a native window in the way, and the same build serves demos and containerized runs. The stub pattern is the price of that, and it is one no-op function per feature.

## Why macOS first

The architecture is not macOS-specific. The same layout, Taskfiles, and bindings build for Windows and Linux, and the generated Taskfiles carry targets for NSIS and MSIX installers, AppImage, deb, and rpm. Those targets stay supported at the Taskfile level — documented, not elaborated.

The depth goes to macOS because macOS is where the platform actively withholds functionality from unsigned builds, and where the recovery path from getting it wrong is longest.

- **Notifications do not authorize outside a packaged, signed bundle.** `task dev`, `task run`, and a bare `bin/<APP_NAME>` will never show one. The feature cannot be proven until the signing pipeline works.
- **Custom URL schemes and single-instance URL relay only work from a packaged `.app`.** The same constraint, on a different feature.
- **Bundle resources are invisible outside a bundle.** `mac.LoadResource` and `mac.ResourceFS` return `ErrNotInAppBundle` under `task dev`.
- **Distribution requires Developer ID signing with a hardened runtime, then notarization, then stapling.** Cross-compiled macOS binaries are unsigned, and `task package` applies only an ad-hoc signature; a real identity and a Mac are still needed.
- **Entitlements differ between development and production.** The scaffold ships none; they are generated by a wizard, and development needs JIT and unsigned executable memory that production must not have.

So on macOS, "it works on my machine" is not a stage the developer passes through on the way to shipping — several features do not exist at all until packaging and signing are correct. Encoding that ordering is most of what the macOS focus is for. It also explains a habit of this plugin's agent that would otherwise look pedantic: it reports which native features were left unverified because no signed bundle was produced, instead of claiming they work.

## The beta trade-off and the pin policy

Wails v3 is at `v3.0.0-beta.25`. It ships near-daily betas and has shipped breaking changes inside the beta series — macOS coordinate normalization, template removals, WebView2 loader changes. Dev-loop reliability is an open blocker for GA, which is why `task build` is the acceptance step and `task dev` is treated as convenience.

The response is a pin, not a pause. A project pins the same tag in `go.mod` and for the `wails3` CLI, and upgrades deliberately; `latest` is never used for either. A bump is a small project of its own: re-run the scaffold check, rebuild, and update every `Verified against` block in the skill's references.

The more interesting rule is the source precedence, which runs:

1. The scaffold and the module source at the pinned tag
2. The documentation at that tag
3. This plugin's skill

That ordering looks backwards for anyone used to trusting documentation first, and it exists because the discrepancies are documented and concrete. The docs describe signing configuration through `SIGN_IDENTITY`, `KEYCHAIN_PROFILE`, and `ENTITLEMENTS` variables in the darwin Taskfile; the scaffold's sign tasks read none of them and call `wails3 tool sign`, taking identity from `wails3 setup signing`. The docs place `config.yml` at the project root; the scaffold puts it at `build/config.yml`. The docs present `TitleBar` as both a constant and a struct. Following the docs in any of those cases produces a build that fails in a confusing way.

The generated project is the artifact that has to compile, so the generated project wins. The skill sits last on purpose: it is a map of a moving target, and when it disagrees with the source, the skill is what gets corrected. Every entry in `references/beta-gotchas.md` names its source for exactly that reason, and entries are deleted when they stop being true.

## When not to use this plugin

A desktop shell is a real cost — packaging, signing, notarization, updates. Several kinds of application should not pay it.

- **Terminal-only tools.** A program that runs in a terminal and needs no window, menu, or tray belongs to the [cli-development](/cli-development/) plugin, which covers argument parsing, command structure, and interactive terminal UIs with frameworks like Bubble Tea.
- **Plain web applications.** An application that runs in a browser and needs no desktop integration — no file system access, no tray, no native menus — belongs to the [web-development](/web-development/) plugin. Wrapping a web app in a desktop shell for the sake of an icon in the Dock buys an update pipeline and a signing chain in exchange for very little.
- **Small native utilities.** A menu-bar utility with no meaningful UI may be simpler in Swift and AppKit than in any webview stack. The [mobile-development](/mobile-development/) plugin carries the Swift expertise that applies to native macOS work.

There is also a shape this plugin deliberately does not promise. Wails v3 has no Touch Bar support, no macOS Services menu integration, no CoreSpotlight indexing, no dock bounce, no custom dock menu, and no `.pkg` output. An application whose value depends on one of those needs a native toolkit, not a webview.

## Cross-plugin collaboration

`wails-go-developer` owns the shape of the application — the layout, the service boundaries, the adapters, the build and signing pipeline — and hands specialist work to agents in sibling plugins rather than reimplementing their expertise.

| Handoff | Agent | What it takes on |
| --- | --- | --- |
| Go implementation, concurrency, performance | `go-architect` (backend-development) | Domain and store packages under `internal/`, which import no Wails types and so need no desktop context |
| React and frontend behavior | `react-specialist` (web-development) | Components, state, routing inside the webview, consuming generated bindings as ordinary typed functions |
| End-to-end testing | `playwright-expert` (code-quality) | Browser-driven tests against the `server` build, which serves the same frontend and bindings |

Each handoff works because of an architectural rule described above. `internal/` importing no Wails types is what lets a Go specialist work without knowing a window exists. Generated bindings being plain typed functions is what lets a React specialist work without knowing Go is on the other end. The `server` build tag is what lets a testing specialist drive the application in a browser. The boundaries that make the code maintainable are the same boundaries that make the collaboration possible.
