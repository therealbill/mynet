# Understanding the diataxis-docs Architecture

The diataxis-docs plugin uses seven specialized agents rather than a single general-purpose documentation writer. This architectural choice reflects the core insight of the Diataxis framework: each documentation type requires fundamentally different writing skills, quality criteria, and constraints. This page explains why the system is structured this way, what each agent's role is, and the trade-offs involved.

## The Problem

Documentation generated by a single agent tends to drift toward a uniform style. A general-purpose writer asked to produce a reference page will include advice. Asked to write a tutorial, it will skip steps and explain concepts instead. Asked to create a how-to guide, it will teach from scratch rather than providing a focused recipe.

The Diataxis framework identifies this as the central documentation quality problem: type mixing. When tutorial content appears in reference pages, or explanation content bloats how-to guides, readers cannot find what they need and documentation becomes progressively less useful.

## Overview

The plugin is organized into three layers:

```
Coordination Layer:    diataxis-orchestrator
                            |
Analysis Layer:     doc-inventory    doc-crosslink-validator
                            |
Content Layer:      doc-tutorial-writer
                    doc-howto-writer
                    doc-reference-gen
                    doc-explanation-writer
```

The **coordination layer** (one agent) manages the overall workflow but never writes content. The **analysis layer** (two agents) examines existing documentation and validates quality. The **content layer** (four agents) writes documentation, with one agent per Diataxis type.

## How It Works

### One Agent Per Diataxis Type

Each content-layer agent is specialized for exactly one documentation type. This specialization is not merely a convention -- it is enforced through each agent's system prompt, constraints, and quality criteria.

The **doc-tutorial-writer** is constrained to produce 90-120 minute learning journeys with checkpoints, progressive skill-building, and a single path. It is prohibited from presenting choices, explaining why things work, or teaching best practices. These constraints exist because tutorials that drift into explanation or reference content fail their primary purpose: getting beginners to a working result.

The **doc-howto-writer** is constrained to 1800 words with a single goal per guide. It assumes existing knowledge and provides recipes, not lessons. Guides that exceed 1800 words almost always contain explanation or reference content that belongs elsewhere.

The **doc-reference-gen** enforces the "no advice" rule -- the single most important quality criterion for reference documentation. It transforms prescriptive statements into factual ones and moves genuine advice to how-to guides. A reference page that says "you should validate inputs" has failed as reference. The correct statement is "input validation is the caller's responsibility."

The **doc-explanation-writer** is constrained to understanding-oriented content: design rationale, trade-offs, mental models. It is prohibited from including step-by-step instructions or bare API specifications. Explanation that drifts into instructions becomes a confusing hybrid that neither explains nor instructs effectively.

### Separation of Analysis from Content

The inventory scanner (doc-inventory) and the quality validator (doc-crosslink-validator) are separate from the content writers for a structural reason: the agents that write documentation should not also judge it.

**doc-inventory** scans and classifies without creating content. Its role is to understand what exists before any transformation begins. It identifies mixed-type pages, coverage gaps, and reorganization opportunities. This analysis informs the orchestrator's plan.

**doc-crosslink-validator** validates after content is written. It checks frontmatter completeness, type purity, link integrity, and cross-linking patterns. By running validation as a separate step, issues are caught that the writing agent's own constraints might miss.

### The Orchestrator Pattern

The diataxis-orchestrator coordinates the other six agents but writes no content itself. This separation of coordination from creation prevents the orchestrator from shortcutting the process by writing documentation directly, which would bypass the type-specific constraints.

The orchestrator's responsibilities are sequencing (which agents run in what order), context passing (docs path, source path, transformation plan), progress tracking (reviewing output between steps), and error handling (maintaining partial progress if an agent fails).

For a detailed discussion of how orchestration works, see {{< ref "explanation/orchestration-model" >}}.

## Why It Is Designed This Way

### Type Purity Through Structural Enforcement

A single agent instructed to "write reference without advice" will eventually include advice. Constraints embedded in a long system prompt erode as context grows. By giving each type its own agent with a focused system prompt, the constraints are structurally reinforced rather than merely suggested.

### Composability

Not every documentation task requires all seven agents. An audit uses only doc-inventory and doc-crosslink-validator. A targeted reference update uses only doc-reference-gen. The modular architecture allows the orchestrator to invoke only the agents needed for a specific task.

### Independent Evolution

Each agent's prompt, constraints, and quality criteria can evolve independently. Improving the tutorial writer's checkpoint logic does not risk degrading reference quality. Adding a new introspection tool to doc-reference-gen does not affect how-to guide generation.

### The "Inherit" Model

All seven agents use `model: inherit`, meaning they run on whatever model the parent Claude Code session is using. This design avoids hardcoding a specific model, allowing the plugin to benefit from model improvements automatically and letting users choose their preferred model tier.

## Trade-offs

| Benefit | Cost |
|---------|------|
| Type purity enforced structurally | Seven agents to maintain instead of one |
| Each agent has focused, effective constraints | Coordination overhead between agents |
| Agents evolve independently | Consistency across agents requires explicit alignment |
| Composable for different workflows | Users must understand which agent does what |
| Analysis separated from creation | Two-pass workflow (write then validate) takes longer |

## Common Misconceptions

**"A single well-prompted agent could enforce all four types."**
In practice, a single agent's type constraints erode as context grows and edge cases accumulate. The structural separation is not about prompt engineering limitations -- it is about maintaining quality guarantees across many documentation pages over time.

**"The orchestrator should write simple docs itself to save time."**
If the orchestrator writes content, it bypasses the type-specific constraints. A "quick" reference page written by the orchestrator might include advice. The overhead of delegating to a specialist agent is the mechanism that ensures quality.

**"Seven agents means seven times the cost."**
Not all agents run for every task. The orchestrator invokes only the agents needed. An audit invokes two. A targeted how-to guide invokes one. The full pipeline of all seven agents runs only for complete restructurings.
